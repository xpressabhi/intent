# Intent Protocol v1

**Status:** Draft

**Protocol version:** `1.0`

## 1. Scope

Intent v1 defines how an agent turns repository intent into a verified change, escalating decisions that need a human. Its adaptive lifecycle is Inception (understand and decide), Construction (implement and verify), and Operations (release and learn when requested). The depth of each phase scales to the change; small changes need no ceremony. The protocol is independent of programming language, AI model, agent, execution host, and review provider.

This document is normative. The words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** express requirements. A conforming implementation MUST preserve recorded intent, repository-defined authority boundaries, and evidence for its outcomes.

**Versioning.** The protocol version identifies the contract revision that governs a repository's records. A record's `protocol_version` MUST name the version under which it was written. Incompatible semantic changes require a new major version published under its own `vN` directories; repositories on earlier majors remain valid under their pinned copies. Compatible clarifications and additions within a major increment the minor version and keep earlier records readable. An implementation MUST reject a record whose version it does not implement; a version it cannot interpret MUST NOT be treated as valid.

## 2. Terms

- **Change:** One bounded, Intent-managed request to modify code.
- **Proposal:** The concise record of requested outcomes, scope, relevant decisions, constraints, and verification. Its detail scales with risk and complexity.
- **Proposal revision:** The exact content of `proposal.md`, identified by an increasing revision number and a content digest.
- **Approval:** An explicit decision by an authorized human reviewer that applies to one proposal revision and may include constraints.
- **Implementation:** Any edit to source, test, build, dependency, or executable-configuration files for the change.
- **Controller:** The component that validates records and state, verifies approval, and mediates the agent's file capabilities.
- **Adapter:** A component that connects Intent to an agent, execution environment, or review provider without changing protocol semantics.

## 3. Required repository records

An adopting repository MUST keep its Intent configuration and change records in version control under `.intent/`. A change MUST have a machine-readable `change.yaml`, a concise human-readable `proposal.md`, and a `conformance.md` record before it is marked `complete`. Record human clarifications as change decisions. Approval evidence MUST be recorded in `review.yaml` or an equivalent provider record only when repository policy requires approval.

The records MUST identify the protocol version, change, current state, proposal revision and digest, scope, and any linked project decisions. When approval is required, its evidence MUST identify the reviewer, their authority, the decision, the reviewed proposal digest, and decision time. Approval constraints MUST be preserved through implementation and conformance review.

The target repository owns these records and its engineering knowledge. Intent MUST NOT require a central database for correctness or portability.

## 4. Adaptive lifecycle and states

The agent MUST first understand the request and relevant repository context, then choose the smallest workflow that can produce and verify the requested outcome. Inception, Construction, and Operations are lifecycle phases, not mandatory documents or approval ceremonies. Operations work is in scope only when requested or required by repository policy.

The agent SHOULD resolve ordinary implementation choices from repository conventions and evidence. It MUST record material assumptions and decisions in the change record. It MUST ask a human only when missing information would materially change the outcome, scope, architecture, data/security/privacy handling, or authority for an action; otherwise it SHOULD choose a reasonable, reversible option and continue. An agent SHOULD continue independent safe work while waiting on a human decision.

| Current state | Event | Next state | Required behavior |
|---|---|---|---|
| `draft` | Outcome is clear and no repository approval gate applies | `implementing` | Record concise scope and verification; implementation may begin. |
| `draft` | Human decision or approval is required | `in_review` | State the specific unresolved decision and its material impact; pause only dependent work. |
| `in_review` | Human provides clarification or requests changes | `changes_requested` | Record the response; implementation remains paused only where it depends on that response. |
| `in_review` | Authorized reviewer approves current revision | `approved` | Record and verify approval evidence. |
| `in_review` | Authorized reviewer rejects | `rejected` | Stop the change; preserve the decision. |
| `changes_requested` | Agent incorporates the response | `draft` | Update the concise change record and reassess whether any human decision remains. |
| `approved` | Required approval is verified | `implementing` | Implement only within the approved scope and constraints. |
| `implementing` | Agent resolves a material issue within delegated authority | `implementing` | Update intent evidence and continue; obtain approval only when repository policy requires it. |
| `implementing` | Material human-only decision appears | `in_review` | Pause dependent work, explain the decision needed, and preserve safe independent progress. |
| `implementing` | Implementation is ready for verification | `conformance_review` | Compare actual outcomes with intent and run relevant checks. |
| `conformance_review` | Outcomes conform | `complete` | Record conformance evidence, including declared test changes and any deviations. |
| `conformance_review` | A gap can be fixed within scope | `implementing` | Continue without new approval unless repository policy requires it. |

An implementation MUST reject unknown states and invalid transitions. A material conflict changes the requested outcome, scope, architecture, interface, data handling, security boundary, or repository-defined approval constraint. Routine choices within those boundaries do not require human approval.

## 5. Human decision and approval boundaries

Human approval is not a universal prerequisite. A change MAY proceed from `draft` to `implementing` when its outcome is clear and repository policy does not require approval. A human response is required only for a material unresolved decision or an action that repository policy reserves for a human. Repository policy MAY require approval for every change or specific paths/actions; that policy takes precedence.

When escalating, the agent MUST present the smallest specific question, explain why the answer changes the outcome or authority, and draft its best recommendation. It MUST continue independent, safe work and MUST NOT ask the human to choose routine details the repository already answers. A response that clarifies intent is not itself approval unless repository policy requires approval and the response explicitly grants it.

When approval is required, the controller MUST verify that:

1. The decision is an explicit approval from a reviewer authorized by repository policy.
2. The approval names the digest of the current proposal revision.
3. The proposal has not changed since that decision.
4. Any approval constraints are available to the implementation agent.

An agent MUST NOT approve its own proposal. A merge, label, comment, or prompt instruction MUST NOT count as approval unless a configured adapter verifies that it represents an authorized human decision for the current proposal digest.

## 6. Proposal revision and digest

Each proposal revision MUST have an increasing positive integer and a SHA-256 digest. The digest is computed over the UTF-8 bytes of `proposal.md` after converting CRLF and CR line endings to LF. A byte order mark MUST NOT be present. No other whitespace or Unicode normalization is applied.

Any edit that changes the canonical proposal bytes MUST increment the revision and produce a new digest. Existing approval evidence for another digest MUST NOT unlock implementation when approval is required. A material change to an approved proposal returns to `in_review` when policy requires renewed approval; otherwise the agent records the revision and continues within its delegated authority.

Approval comments and constraints are review evidence, not edits to `proposal.md`. They MUST be recorded with the approval and passed into implementation. Changing approval constraints after approval requires a new approval for the updated review record.

## 7. Intent and conformance evidence

The intent record answers: **What outcome is requested, what decisions constrain it, and how will we know it worked?** Keep it short for routine changes. Expand it when complexity, risk, or an explicit repository policy warrants deeper planning. Alternatives and formal human review are needed only when they help resolve a material decision or policy gate.

Existing behavior is preserved by default. The proposal MUST declare any intended change to a pre-existing test and any behavior the change intentionally alters; otherwise the change MUST leave existing behavior and pre-existing tests unchanged. A failing pre-existing test MUST NOT be modified, skipped, or deleted to make it pass; it MUST be treated as a regression and recorded as a deviation. A change MAY declare the path globs it intends to touch; when declared, verification MUST reject undeclared paths. Repository policy MAY mark test paths as protected; an undeclared edit to a protected path is invalid and a controller MUST deny it.

The conformance record answers: **Did the change produce the intended outcome within repository constraints?** It MUST link to the current intent revision, disclose material deviations, record significant agent decisions/assumptions, and summarize verification evidence. When approval was required, it MUST also identify the approved proposal digest and preserve approval constraints.

When approval is required, the proposal MAY be submitted through a configured review provider. Provider-specific branch, pull-request, and identity mechanics belong to adapters; protocol semantics remain provider-neutral.

## 8. Git and worktree behavior

Any commit MUST contain only the current change's related files. An implementation MUST NOT stage or commit the entire working tree by default. Unrelated existing work MUST be preserved and excluded from the change's commit.

Implementation MAY proceed in a separate branch or other isolated change boundary. The selected Git workflow MUST retain traceability from requested outcomes through implementation and conformance evidence; when approval was required, retain its revision and constraints too.

## 9. Fail-closed behavior

The controller MUST deny implementation access to operations that violate repository policy, and MUST pause dependent work when:

- required approval is missing, stale, malformed, or tied to a different proposal digest;
- reviewer identity or authority cannot be verified;
- a review provider is unavailable and approval cannot be verified;
- the change state or state transition is unknown or invalid; or
- implementation reaches a decision reserved for a human by repository policy.

An unavailable dependency or uncertain record MUST NOT be interpreted as approval. Once a failure is resolved, the controller MUST revalidate the current intent and any required evidence before granting access. Uncertainty that does not materially affect the outcome is recorded as an assumption, not treated as a universal stop condition.

## 10. Conformance

An implementation conforms only if it can demonstrate that the requested outcomes and repository boundaries are preserved, material human decisions are escalated, routine work proceeds without unnecessary approval, required approval is bound to the exact intent revision, and conformance evidence records decisions and verification.

Protocol scenarios are published under `conformance/v1/`. A controller or adapter claiming enforcement MUST additionally test its actual permission boundary; documentation or prompt checks alone are insufficient.
